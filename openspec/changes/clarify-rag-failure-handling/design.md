## Context

启动流程 `initialise()` 和命令行自检在取得维度后都会写回模型信息。上传管线替换同名文档时会先删除旧片段，因此存储兼容性判断需要早于替换操作。问答路由已有统一的检索错误事件，文档列表也已有加载失败视图，这两处都可复用。

## Goals / Non-Goals

让存储层如实提供读取结果，由自检和写入入口据此决定如何处理。检索和界面只调整提案列出的分支。本次范围之外包括重写供应商协议、调整融合算法及迁移历史数据。

## Decisions

### 1. 区分可初始化的空库与无法验证的已有库

| 实际结果 | 自检及写入行为 |
| --- | --- |
| 查询成功、没有 schema 记录，父子集合均无数据（包含集合尚未创建） | 允许首次初始化并记录模型和维度 |
| 已有 schema，模型、维度与当前配置匹配 | 复用已有元数据；重复启动和自检无需写回 |
| Milvus 查询失败，或无法确认已有集合是否为空 | 报告 `store_schema: unreachable`，保留原记录 |
| 已有 schema 无法解析、缺少模型或维度，或已有片段却缺少 schema | 报告 `store_schema: contract_mismatch`，提示检查或恢复元数据 |
| 已记录的模型或维度与本次探测冲突 | 报告 `store_schema: misconfigured`，展示原值和当前值，提示显式重建 |

让 `read_meta()` 只在确实没有记录时表达缺失，查询错误和已有记录的解析错误交给自检分类。用同一个兼容性判断指导启动、自检脚本以及服务的建库入口，移除 `run_selfcheck()` 中会丢失该检查项的兜底。只有元数据缺失时才需区分空库与已有数据。仅凭已探测到向量维度就调用 `write_meta()` 会覆盖诊断所依赖的旧值。

服务继续启动以展示健康报告。存储校验失败时，在上传调用 `pipeline.ingest()` 前返回已有上传失败事件并说明原因，保住同名文档的登记状态和向量。修复配置或恢复元数据后，重新启动即可按相同规则恢复。命令行自检输出对应原因，并为存储校验或首次记录失败返回非零退出码。

### 2. BM25 执行异常走已有检索错误事件

保留空索引、空查询及无有效分词的正常返回。移除包住 BM25 查询的通用捕获，让执行错误到达已有的问答路由，由路由记录异常并发送 `error`，结束本次回答。若选择故障时仅用向量继续回答，还需要把降级状态传给用户；本次采用项目已有的检索失败行为。重排服务的可用性由独立规格约定，仍可降级。

### 3. 在生成结果的那一层保证内部约定

`_fuse()` 的两路排名和候选字典来自同一批 ID，按键直接获取候选。`Reranker._parse()` 已拒绝空结果、越界和重复下标，`_rerank()` 可直接映射校验后的结果。保留输入候选为空、供应商错误、部分合法结果的处理，以及补入未打分候选的原有顺序。再写一遍边界校验只会让调用方多出一套跳过错误数据的规则。

### 4. 文档列表按 HTTP 状态和响应约定渲染

`loadDocuments()` 先检查 `response.ok`，再解析成功响应中的 `documents` 数组。网络失败、非成功状态、无效 JSON 或缺少约定数组都进入已有的“加载失败”视图。只有长度为零的数组展示“还没有文档”。改动局限于这个请求，复用当前页面的错误处理。

## Risks / Trade-offs

- BM25 故障会中断当次问答。用“向量有命中且 BM25 抛错”和“关键词正常零命中”两组用例确认用户能区分这两种结果。
- 已有数据却没有可靠元数据时，上传会被阻止。保留原始记录，让操作者恢复可信元数据或显式重建。不能从向量维度反推出历史模型身份。

## Migration Plan

复用现有 schema 记录与健康状态。部署后先运行自检，确认原模型名和维度可读，再尝试上传。回退应用版本无需转换数据；旧版本启动可能改写已有元数据，应先核实配置与原库一致。
