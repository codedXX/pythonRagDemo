## Context

`build_services` 用 `settings.sqlite_path()` 构造登记表。上传按文件名定位要替换的旧版本，删除操作通过登记记录的 `doc_id` 清理 Milvus。迁移如果更改文件名匹配方式或重算标识，后续上传和删除就可能作用到错误的片段。

## Goals / Non-Goals

目标是将服务和迁移命令接到同一个 MySQL 登记库，并维持既有 API 行为。向量、BM25 索引、本地嵌入缓存以及跨实例并发上传的协调均在本次范围之外。

## Decisions

应用和迁移命令均在宿主机运行，通过 TCP 连接本机原生安装的 MySQL。两者共用连接配置，`mysql.host` 默认为 `127.0.0.1`，`mysql.port` 默认为 `3306`。本机实例使用其他端口时可通过配置覆盖。部署和验收均以宿主机 MySQL 服务为准。

1. **连接与配置。** 增加顶层 `mysql` 配置组，包含 host、port、database、user、password，复用 YAML 加载和 `RAG__MYSQL__*` 环境变量覆盖机制。将 password 纳入配置脱敏。部署端预建数据库并提供账号，服务在该库初始化表与索引。选择同步 PyMySQL 驱动以匹配现有同步接口，按登记操作获取和关闭连接，写操作显式提交或回滚。同一操作的写入和结果读取共用事务。仅维护一张表，当前无需引入 ORM 或连接池。
2. **表和查询。** 使用 InnoDB，以 `doc_id` 为主键，文件名和状态建普通索引。文件名采用支持完整 Unicode 的文本列、前缀索引和精确比较，确保大小写、重音、尾随空格参与匹配。保留各列表现有排序。显式以 UTC 写入秒级 DATETIME，读出后转换为原有的 `YYYY-MM-DD HH:MM:SS`。重复主键使用原子更新，保留创建时间，只重置本轮入库字段。失败原因沿用原有截断语义。
3. **离线复制。** 提供独立的 `scripts/migrate_registry.py`，输入为显式指定的 SQLite 文件和项目 MySQL 配置。命令只读打开源文件，复用目标表的初始化逻辑。先建表，然后在单个数据事务内读取目标、写入并按 ID 对照所有字段后提交。完全一致的非空目标直接报告成功，其他非空目标报告差异并退出。直接复制九个字段，调用入库流程会重置状态并触发模型或 Milvus 写入，因此迁移命令独立于服务组装。

## Risks / Trade-offs

- 切换期间仍有写入 → 暂停上传和删除，等待在途任务结束后停服务。遗留的 staging 记录按原状态迁移。
- 文件名比较规则影响同名替换 → 在真实 MySQL 用仅大小写、重音或尾随空格不同的文件名验证精确匹配。
- MySQL 成为服务启动依赖 → 在部署说明中列出连接参数和建表权限，连接或初始化失败时提示数据库和失败原因，日志隐藏密码。

## Migration Plan

1. 新部署配置 MySQL 后直接启动。已有部署先停止写入，备份已关闭的 SQLite 库，保留旧版应用和配置。
2. 对预建的目标数据库运行迁移命令。按状态核对数量，逐条按 ID 校验字段；只有全部一致才切换服务。
3. 在写入口仍关闭时启动新版，使用文档列表和现有 active 文档做只读检索验证，再恢复上传和删除。
4. 恢复写入前若验收失败，可停新版、恢复旧配置并以旧库启动。MySQL 已接受新写入后，应先停写并对账新增、替换和删除操作，直接回切旧快照会使登记数据与 Milvus 脱节。
