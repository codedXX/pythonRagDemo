## Context

本项目为全新空仓库。设计受以下**已实测**的环境事实约束（非推断）：

| 事实 | 实测结果 | 设计含义 |
|---|---|---|
| Milvus | standalone `v2.6.23`，`127.0.0.1:19530`，healthy，来自 `/Users/dengyixuan/milvus` compose 项目 | 完整 standalone，非 Lite；但不能假设可随意重启该容器 |
| pymilvus | `3.0.3` 连 `2.6.23` 成功 | 客户端取 3.x，无需降级到 2.6.x |
| 一致性 | 默认一致性下 insert 后立即 count=0 / search 命中 0；`flush()` 后可见；`consistency_level="Strong"` 下立即可见 | **必须显式 Strong**，否则入库后不可查 |
| 无向量 collection | 建表失败 `schema does not contain vector field`；有向量字段但无索引也失败；`dim=1` 失败（下限 2） | 父块表须带 dim=2 占位向量并建索引（见 D1） |
| VARCHAR 上限 | `max_length=65535` 可存 5000 字符文本；`output_fields=["*"]` 会带回向量字段 | 文本字段够用；翻转 active 时须整行 upsert |
| 百炼 embedding | `POST /compatible-mode/v1/embeddings` → 400（存在）；错误体为 OpenAI 风格 | 可用 `openai` SDK |
| 百炼 rerank | `POST /compatible-mode/v1/rerank` → 404；`POST /api/v1/services/rerank/text-rerank/text-rerank` → 401（存在），错误体为 DashScope 风格 | **rerank 必须手写原生 client，不能复用 openai SDK** |
| 中转站 | `/v1/chat/completions` 401（存在）、`/v1/messages` 401（存在）、`/v1/models` 401（存在）、`/v1/rerank` 404（不存在）、`/v1/completions` 404 | 双协议网关；无 rerank，重排只能走百炼 |
| 路由推断方法 | 无 key 时 `POST /v1/models` 与 `/v1/completions` 返回 404 而非 401，说明路径在鉴权前判定 | 401=存在、404=不存在的推断可靠 |
| 模型名 | `qwen3.7-text-embedding-flash` / `qwen3.7-text-rerank` **无法核实**（本会话 web 通道不可用） | 必须用启动自检消解，不得硬编码假设 |
| 既有数据 | Milvus 中已有 `rag_demo`（27 行）、`rag_chunks`（10 行）历史实验 collection | 新项目用独立命名，不读写删除它们 |
| 运行环境 | macOS arm64，8 核 / 16GB；pyenv Python 3.13.12；`uv 0.13.9` 已装 | 锁 Python 3.13；避免本地推理模型 |

**规模目标**：同时入库几十份文档、万级 chunk 以内。这决定 BM25 可全量内存式重建，无需增量索引或落盘索引。

## Goals / Non-Goals

**Goals:**

- 让「混合检索 + 语义分块 + 父子文档 + RRF + 重排」这条链路**每一段都可单独观测和调参**，这是学习型项目的第一价值。
- 外部依赖的不确定性（模型名、维度、限流）在启动期暴露，运行期不产生意外失败。
- 检索结果可解释：能回答「这条内容是被哪一路召回的、RRF 给它排第几、重排后升了还是降了」。

**Non-Goals:**

- 不做 OCR：扫描件显式拒收优于产出垃圾。
- 不做多知识库隔离：单 collection 全局可见。
- 不做用户鉴权与多租户：本地学习用途，API 不设认证。
- 不做增量 BM25 索引：万级规模全量重建在秒级，复杂度不值。
- 不引入异步任务队列（Celery/RQ）：单进程 + 内存任务表足够。
- 不做 RAGAS 评测：拆到后续 `ragas-eval` 变更，避免评测依赖污染主依赖树。

## Decisions

### D1: 存储用 Milvus 双 collection（child / parent），而非单表自引用

**选择**：`rag_child` 存子块与真实向量，`rag_parent` 存父块原文（附 dim=2 常量占位向量，见下），以 `parent_id` 关联。

**理由**：父子两层的数据量与访问模式完全不同。子块需要向量索引、被高频 ANN 检索；父块只需按主键批量点查。混在一张表里会让向量索引包含永不参与检索的父块向量，浪费且污染候选集。

**⚠️ 实测修正（实施阶段发现）**：原设计写的是「父块表不需要向量字段」，**这条对 Milvus 是错的**。实测确认了三条硬约束：

```
无向量字段              → 建表失败 "schema does not contain vector field"
有向量字段但无向量索引  → 建表失败 "there is no vector index on field [...]"
有向量字段 + 向量索引   → 成功
dim=1                  → 建表失败 "invalid dimension: 1. should be in range 2 ~ 32768"
```

**修正后的做法**：父块表增加一个 `dim=2` 的 `placeholder` 向量字段并为其建索引，值恒为常量 `[0.0, 0.0]`。**该向量不调用 embedding API**，因此原设计中「不想为父块浪费 embedding 调用」的目标仍然成立——被放弃的只是「父块表完全没有向量字段」这一形式。

**替代方案 A**：父块文本改存 SQLite。**否决**：父子数据分属两个存储，SQLite 异常时父块变孤儿，检索链路会静默降级；且失去 Milvus 层面的引用完整性。
**替代方案 B**：父子合并单 collection，父块正文冗余进每个子块行。**否决**：存储膨胀约 4 倍（一个父块平均带 4 个子块），且父块更新需改多行。

**替代方案**：单 collection + `level` 字段区分，查询时过滤。**否决理由**：ANN 检索会在过滤前遍历候选，父块向量纯属噪声。

### D2: 一致性级别显式设为 Strong

**选择**：建 collection 时 `consistency_level="Strong"`。

**理由**：实测默认一致性下，insert 完成后立即 count 得到 0、search 命中 0；`flush()` 后正常。若不处理，会出现「上传完成后立刻提问却查不到」——这类 bug 从日志看一切正常，极难定位。

**替代方案 A**：每次写入后 `flush()`。**否决**：需在每条写入路径记得调用，易漏；且 flush 是重操作。
**替代方案 B**：查询侧用 `consistency_level=Bounded` 并在 UI 上提示"稍等几秒"。**否决**：把正确性负担转嫁给用户，且延迟不可预测。

**代价**：Strong 需等待副本确认，延迟略高。但单机 standalone、万级数据，代价可忽略，换来干净的语义。

### D3: BM25 在 Python 侧（bm25s + jieba），不用 Milvus 原生稀疏向量

**选择**：`bm25s` 做稀疏召回，`jieba.cut_for_search` 做中文分词；抽象 `LexicalIndex` 接口以备切换。

**理由**：Milvus v2.6.23 standalone 支持原生 BM25，但本项目首要目标是**可观测**：两路召回的原始排序、RRF 融合前后位次变化、分词命中情况，全部需要能在应用侧打印和单测。原生方案在服务端融合，等于把最需要观察的部分变成黑盒。此外 jieba 的用户词典与停用词表完全在自己手里，中文效果可迭代。

**替代方案**：Milvus 原生 `SPARSE_FLOAT_VECTOR` + `BM25BuiltInFunction`。**否决理由（当前阶段）**：丧失中间结果可视性；且需要更复杂的 analyzer 配置。保留接口，后续可作为 `LexicalIndex` 的另一实现。

**代价**：应用侧维护索引、启动需重建（见 D4）；规模上限低于原生。已知并接受。

### D4: 稀疏索引以 Milvus 为唯一事实源重建

**选择**：进程启动时、以及每次入库/删除成功后，从 `rag_child.active == true` 拉取文本重建 BM25 索引；重建入口带 debounce。

**理由**：若从磁盘原文重建，一旦「Milvus 有数据但文件已被删/改」，两路召回就指向不同现实，融合结果不可解释。Milvus 作为唯一事实源保证两个通道看到同一份语料。

**代价**：启动需一次全量拉取。万级 chunk 约秒级，可接受。

### D5: 分块采用「结构优先 + 语义兜底」，且父子为包含关系

**选择**：父块由结构边界决定（MD 标题层级 / PDF 版面块），仅在结构段仍超限时才用句子嵌入做断点检测；子块在父块内部按固定大小机械切分并带重叠。

**理由**：语义分块需要先对句子做一次 embedding，"切完再 embedding 一遍"意味着两遍开销。实测估算 30 页中文约 600 句 → 句子 pass 约 60 次批量调用，块 pass 约 15 次，**第二遍只贵约 25%**。因此不值得为省这 25% 去用句子向量池化近似块向量（会引入说不清的检索质量损失）。而结构优先能直接消掉大部分语义检测开销：Markdown 有标题层级、PDF 有版面块，真正需要语义兜底的比例很低。

**替代方案 A**：纯语义分块（全文档句子嵌入找断点）。**否决**：对 MD 这种结构清晰的文档纯属浪费，且结构信息被丢弃。
**替代方案 B**：块向量 = 句子向量池化。**否决**：池化向量与直接嵌入文本的向量分布不同，检索质量损失无法量化，省 25% 不划算。
**替代方案 C**：固定长度滑窗切分。**否决**：会切断段落和标题，父子文档的意义大打折扣。

**必要配套**：句子向量与块向量**均按内容 hash 落盘缓存**。调 chunk 参数会反复重跑，缓存让迭代从"每次都花几十次调用"变成"只算变化的部分"。

### D6: Rerank 输入带面包屑，LLM 输入用父块

**选择**：重排时提交的文本为 `source_name > heading path ｜ child text`；生成时提交父块正文。

**理由**：子块是碎片，单独看常常语义不完整（如"如下表所示"），裸文本会拿到不公正的低分。补上面包屑后重排能理解上下文。而生成阶段需要的是完整论述，因此用父块。**两个阶段各取所需的粒度。**

### D7: RRF 在应用侧手算，参数可配置

**选择**：`score = Σ 1/(k + rank_i)`，k 默认 60，可配置。

**理由**：与 D3 同源——只要两路召回在应用侧，融合自然也在此处，便于打印每一路的贡献与最终位次。RRF 只用名次不用分数，天然规避了 BM25 分值与余弦相似度不可比的问题。

**替代方案**：加权分数融合。**否决**：需要分数归一化，而两路分数分布差异大且随语料变化，归一化参数会变成新的调参负担。

### D8: 父块去重后需回填

**选择**：重排候选数（如 30）显著大于最终供给数（如 8）；父块级去重后若不足最小上下文数，从重排剩余列表继续补。

**理由**：重排 top-N 中很可能多条来自同一父块，去重后会"缩水"。若不回填，配置的上下文数形同虚设。

### D9: 入库原子性用 active 标志，而非先删后写

**选择**：所有写入以 `active=false` 落库，成功后统一翻 `active=true`；检索恒带 `active == true` 过滤。同名文档重传时，先完成新数据写入并翻转，再清理旧记录。

**理由**：避免中途失败留下"半篇文档"被检索到。也避免先删后写导致写入失败时新旧全无。

### D10: 异步任务用内存任务表 + SSE

**选择**：上传接口立即返回任务 ID，后台线程执行，进度通过 SSE 推送 `stage` 事件。

**理由**：30 页 PDF 的解析+分块+向量化需数十秒，同步 HTTP 会超时且无反馈。万级规模下内存任务表足够，重启丢失任务可接受（文档状态以 SQLite 为准，可重新上传）。

**替代方案**：Celery/RQ + Redis。**否决**：为单机学习项目引入消息队列与额外容器，收益不匹配。

### D11: SSE 事件顺序固定为 sources → token*

**选择**：检索完成即先推送 `sources` 事件，再推送生成的 token 流。

**理由**：多轮 rewrite + 检索 + 首 token 约 2~3.5 秒。先给出"正在参考这 N 篇"，让等待有内容，显著改善体感。

### D12: 配置双轨，密钥优先环境变量

**选择**：`config.example.yaml`（入版本库，密钥留空）与 `config.yaml`（.gitignore）。加载优先级：环境变量 > `config.yaml` > 默认值。

**理由**：既支持"手动填配置文件"的诉求，又为将来容器化留出环境变量入口。示例文件入版本库让仓库可克隆即可跑。

### D13: 维度不硬编码，启动期探测

**选择**：启动自检对 embedding 发一条探针文本，从返回向量长度取得维度，用于建表并写入 meta；若已存在 collection 且记录的 `{model, dim}` 与当前配置不符，明确报错要求重建。

**理由**：维度在建 collection 时锁死，事后无法修改。而用户给的模型名无法预先核实，硬编码维度是最大的返工风险。探测把它变成配置问题。

### D14: 前端零构建，FastAPI 托管静态文件

**选择**：原生 HTML + CSS + ES modules，无打包器；对话 Markdown 渲染用轻量库。

**理由**：符合"静态页面"的原始诉求；省掉 Node 构建链，改一行刷新即可见。规模上完全够用。

## Risks / Trade-offs

- **模型名不可核实**（`qwen3.7-text-embedding-flash` / `qwen3.7-text-rerank` 可能不存在或名称有误）→ 全部配置化，并由 D13 启动自检在首次运行时明确报错；名字错了只改配置一行，不改代码。
- **Embedding/rerank 是两套协议，混用会静默失败** → 显式两个适配器，各自独立的请求体构造与响应解析，各自独立单测；健康检查分别验证。
- **一致性默认值导致"刚入库查不到"** → D2 显式 Strong；并在集成测试中断言"入库后立即检索可命中"。
- **重排导致上下文数缩水** → D8 回填机制；测试构造"多条命中同一父块"的用例。
- **扫描版 PDF 产出空内容** → 解析后按字符密度阈值检测并显式拒收，绝不让空文档入库。
- **BM25 与 Milvus 不一致（幽灵文档）** → D4 以 Milvus 为唯一事实源重建；删除路径同样触发重建。
- **多轮 rewrite 抬高首字延迟至 2~3.5s** → 无历史时跳过；问题无指代且长度足够时跳过；先推 sources（D11）降低感知延迟。**评测时必须关闭多轮**，否则与单轮基线不可比。
- **轮询百炼可能触限流** → 批大小可配、指数退避重试、非重试错误（401/未知模型）立即失败并给出配置化提示；向量缓存（D5）减少重复调用。
- **大父块挤占上下文预算** → 设上下文预算上限，超限时以命中子块为中心截取（对应 hybrid-retrieval 的 Oversized parent handling）。
- **内存任务表重启即失** → 可接受；文档状态以 SQLite 为准，任务丢失表现为需要重新上传，不会产生脏数据。
- **Milvus 容器重启后数据仍在，但 BM25 需重建** → 启动流程已包含重建，无额外风险。
- **与既有 `rag_demo` / `rag_chunks` collection 混淆** → 新集合固定命名 `rag_child` / `rag_parent` / `rag_meta`；代码中不引用旧集合，不做自动清理以免误删。

## Migration Plan

无既有生产数据，无需迁移。首次运行顺序：

1. `uv sync` 建立环境；复制 `config.example.yaml` 为 `config.yaml` 并填入两个密钥。
2. 运行启动自检脚本，确认 embedding 维度、rerank 响应结构、生成模型与流式能力（此步会暴露模型名是否有效）。
3. 启动服务，自检结果写入 meta collection 并按探测到的维度建表。
4. 通过页面上传文档，验证「入库后立即可查」。

**回滚**：本变更为新增，不影响既有 collection。如需清除，删除 `rag_child` / `rag_parent` / `rag_meta` 三个 collection 与本地 SQLite 文件即可。

## Open Questions

- 中转站的 `claude-sonnet-5` 是否支持 function calling 尚未验证。这**不影响**本变更（生成阶段只用普通流式补全），但会影响后续 `ragas-eval` 变更中 RAGAS 的结构化输出解析。留待该变更前用一条探针验证。
- 百炼 embedding 的批量上限与 QPS 配额未知。批大小已配置化，运行中可调，不改变设计。
- PDF 版面块的具体切分粒度（按行块还是按字号聚类）需要在实际文档上试调；两种都属实现细节，不改变 spec 行为。
