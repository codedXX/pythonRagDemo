## Context

上传路由在 `stream()` 内定义进度回调和工作线程，用队列和共享字典将进度、结果送回响应。进入 `ingestion.py` 后，`_parse()` 再经过 `parse_document()`、`PdfParser.parse()` 才打开 PDF。浏览器在整个请求期间解析事件帧。

## Goals / Non-Goals

读者从上传路由进入 `ingest()`，能在同一个函数内看到格式分支、各步的数据传递、成功条件和失败记录。此轮集中整理导入路径。切块算法、检索排序和问答流各有独立职责，沿用现有实现。

## Decisions

1. **把批量上传写成普通同步路由。** FastAPI 执行同步路由时可承载现有阻塞式解析和存储调用。按输入顺序逐个读取 `UploadFile.file`、校验大小、检查存储就绪、调用入库并收集结果；每份文件处理完再读取下一份。存储检查要先于修改同名登记。成功后按现有路径刷新关键词索引。删除上传专用 job ID、线程、队列与进度回调。保留异步路由再为阻塞调用逐层调度会增加阅读成本。
2. **由一个入库入口串起数据流。** 在 `ingest()` 里直接按已支持的扩展名与 PDF 文件头选择 `parse_pdf()` 或 Markdown 解析函数。PDF 分支进入的函数直接打开文件，依次提取文本和位置、识别扫描件、过滤页眉页脚、产生带页码的段落。需要独立阅读的文字处理规则放在解析函数所在的文件。删除只转调的阶段方法、解析分发和仅为调用一次而创建的解析器对象；相应调整仓库内的调用方和测试。
3. **把实际入库顺序写在读者看得到的位置。** 同一入口依次登记、解析、切块、生成向量、处理旧版本、写入未激活的父子块、激活并登记统计。保留存储和模型调用处有实际用途的封装。将重复的父子块字段搬运收敛到写库处，保留向量归一化、来源字段、存储长度限制及激活规则。用当前操作标识为失败记录提供阶段和原因，删除进度对象和成功阶段广播。每个文件的异常在该文件边界转换为最终结果。
4. **页面只读一次响应。** 前端继续提交 `files` 表单并调用 `response.json()`，通过数组顺序对应本次提交的文件，使同名文件也能分别呈现结果。沿用文档和健康信息刷新逻辑。问答处理继续使用自己的事件解析路径。

## Risks / Trade-offs

- 大批文件在最后一份处理结束后才显示全部结果 → 请求期间使用一个等待提示，用户可选择较小批次。
- 合并函数时可能误删与进度混在一起的业务处理 → 用扫描件、已有同名文档、写入失败、成功后立即检索来验证失败原因、文档可见性和引用。
- 旧页面把结果当事件流解析 → 同批部署静态资源与后端，并在 README 标明新响应格式。

## Migration Plan

同步发布上传接口与静态页面；自有脚本将事件读取替换为遍历 `results`。本次只调整请求处理与代码组织，需要回退时一并回退程序和静态资源即可，已有文档沿用原登记和存储格式。
